\chapter{Conclusion and Next Activities}

\section{Conclusion}

This work developed and evaluated a hybrid framework for mission-driven ROS~2 configuration. The framework combines static repository analysis, an explicit system model, bounded language-model reasoning, deterministic capability realization, validated parameter modification, and template-based artifact generation. Its central design decision is to use the language model only where semantic interpretation is required, while keeping repository facts, dependency resolution, admissible configuration values, file structure, and rendering under deterministic control.

The implemented prototype analyzes ROS~2 Python nodes, launch descriptions, and parameter files without executing them. It integrates the extracted facts into a versioned deployment model containing component activation, parameter provenance, interfaces, remappings, and known communication relationships. From this model, the implementation derives 109 writable physical configuration locations from 114 effective parameter occurrences. This distinction prevents several runtime occurrences of the same underlying configuration value from being treated as unrelated writable parameters.

Natural-language reasoning is divided into three specialized calls. Capability reasoning selects an implementation, or explicit deactivation, for each supported capability. Parameter selection chooses identifiers only from a capability-conditioned, top-ten semantic retrieval context. Parameter-value reasoning receives only the validated selection and generates typed replacement values. The model never writes YAML or launch code directly. Structured responses are checked against schemas, active-component restrictions, retrieved identifiers, types, allowed values, numerical bounds, and parameter relationships before deterministic templates can materialize a configuration.

The experimental progression shows that this decomposition and the contracts between stages were more important than adding examples alone. The initial production-prompt baseline achieved 38.7\% capability exact match, 0.7\% parameter-selection exact match, and no jointly exact missions. Few-shot prompting improved partial recognition but did not improve exact parameter selection. Introducing the unified staged evaluator, semantic metadata, top-ten bounded retrieval, hidden retrieval rankings, active-component filtering, separated selection and value reasoning, and validation-guided correction increased joint exact match to 40.0\%.

The final minimal capability contract produced the strongest results. On 150 mission paraphrases, capability exact match reached 96.7\%, capability micro $F_1$ reached 98.5\%, parameter-selection exact match reached 88.7\%, and parameter-value exact match reached 88.7\%. A total of 132 missions were jointly exact, corresponding to 88.0\%, while 148 missions, or 98.7\%, completed all applicable validated stages. Only two cases ended in runtime or validation errors. For the 80 parameter-changing missions, retrieval contained every expected parameter within the top five, selection exact-set accuracy was 83.8\%, and individual-value accuracy was 96.4\%. These results confirm that value generation is comparatively reliable once the complete correct parameter set has been identified.

The results also demonstrate the importance of the simplified capability representation. Each capability is represented directly by its selected implementation, while \texttt{null} is reserved for explicit deactivation. Unmentioned capabilities retain registry-defined defaults, and choosing a capability implementation does not imply tuning its runtime parameters. Removing inference-control fields such as \texttt{selection\_basis} reduced output ambiguity and prevented irrelevant representational differences from being scored as semantic failures.

The principal contribution is therefore not unrestricted natural-language control of a robot, but a reproducible and auditable boundary between probabilistic interpretation and deterministic system modification. Repository-derived evidence limits what the model can select; capability realization determines what may be active; validation prevents malformed or ungrounded conclusions from reaching the renderer; and templates preserve syntactic correctness and unchanged baseline values. The final results show that this architecture can provide strong performance on the evaluated AntRobot mission distribution while retaining explicit failure containment.

Operational reliability has not yet been established. The benchmark contains paraphrases of fifteen verified intents, uses one local model, and contains only supported requests. The experiments are single runs, and the successive system versions combine several changes rather than isolating each one. Moreover, structural validation of generated artifacts is not equivalent to successful behavior in simulation or on a physical robot. The reported 88.0\% joint exact-match result should therefore be understood as strong evidence for the proposed architecture on the current dataset, not as a claim of general natural-language autonomy.

\section{Next Activities}
\label{sec:next-activities}

The next activities should consolidate the current result before expanding the system:

\begin{enumerate}
    \item \textbf{Freeze and independently review the benchmark.} Complete author or second-annotator review of all paraphrases and reference annotations, record disagreements, and create fixed development and held-out partitions. Future prompt or implementation changes should use only the development partition before one final held-out evaluation.

    \item \textbf{Extend the outcome space.} Add independently annotated unsupported, contradictory, and genuinely ambiguous missions. This is necessary to measure unsafe acceptance, unsupported-request rejection, clarification precision and recall, and behavior when no valid configuration exists.

    \item \textbf{Analyze the remaining end-to-end errors by boundary.} Classify the eighteen missions that are not jointly exact into capability, retrieval, selection, and value failures. The two runtime or validation errors should be distinguished from semantically valid but incorrect structured outputs. This analysis should determine whether the next improvement belongs in metadata, retrieval, prompting, validation, or the capability registry.

    \item \textbf{Run controlled ablations.} Hold the dataset, capability contract, model, and prompts fixed while independently varying deterministic evidence, LLM-derived aliases and user expressions, typed relationships, graph expansion, active-component filtering, candidate count, and validation-guided retry. An oracle-capability experiment should isolate parameter reasoning, and an oracle-selection experiment should isolate value reasoning.

    \item \textbf{Measure repeatability and model dependence.} Repeat the final experiment to estimate run-to-run variance and confidence intervals. Compare alternative local models under the same frozen prompts and contexts, reporting semantic accuracy, validation failures, latency, memory requirements, and token usage rather than accuracy alone.

    \item \textbf{Improve robustness across linguistic variants.} Although nine of fifteen intent groups were jointly correct for all ten paraphrases, six groups still contained at least one failure. Targeted development should focus on negation, shorthand, multi-clause requests, implicit units, coupled physical properties, and the distinction between selecting an implementation and tuning its parameters.

    \item \textbf{Validate generated behavior in ROS~2.} Execute generated bundles in an isolated ROS~2 environment and verify node activation, topic and frame connectivity, parameter application, lifecycle transitions, and recovery from launch failures. Follow simulation testing with controlled experiments on the physical AntRobot platform where safe and feasible.

    \item \textbf{Evaluate transfer beyond the current repository.} Apply the extraction, integration, and reasoning pipeline to additional ROS~2 workspaces with different launch structures and configuration conventions. This will show which parts of the method generalize automatically and which still depend on AntRobot-specific registry knowledge or templates.
\end{enumerate}

These activities move the project from a high-performing repository-specific prototype toward a validated configuration assistant. The immediate priority is not to broaden autonomous action, but to verify the final result under frozen data, characterize the remaining failures, and demonstrate that accepted configuration plans produce the intended behavior in simulation and on the robot.
