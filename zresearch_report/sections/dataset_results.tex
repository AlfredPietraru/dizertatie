\chapter{Dataset and Experimental Results}
\label{chap:dataset-results}

This chapter describes the construction of the AntRobot train and test mission datasets, the evaluation protocol used for the language-model stages, and the resulting experiments: capability interpretation and parameter reasoning evaluated in isolation, and the complete pipeline evaluated end to end. Configuration rendering, generated YAML files, and generated launch files are outside the scored boundary; the reported results concern the three language-model stages and their deterministic validation.

\section{Dataset and Evaluation Methodology}
\label{sec:extended-datasets}

Each dataset entry began with a verified structured intent and its corresponding reference annotation. A text-generation model was then used only to express that intent in varied natural-language forms. Because the expected capabilities and parameters were defined beforehand rather than inferred by the model, the reference labels remained independent of the generated wording.

The current benchmark consists of two independently frozen datasets, \texttt{antrobot\_train\_mission\_dataset\_v1.jsonl} and \texttt{antrobot\_test\_mission\_dataset\_v1.jsonl}, built to separate development from held-out evaluation and to cover the full outcome space rather than supported requests alone. Fifty train seeds (\texttt{seed-101}--\texttt{seed-150}) and fifty test seeds (\texttt{seed-151}--\texttt{seed-200}) were authored from capabilities and parameters that exist in the extracted AntRobot system model, each with a canonical intent, a sparse capability annotation, any explicitly requested parameter values, and descriptive strata. Each split spans three outcomes: \texttt{supported}, \texttt{unsupported}, and \texttt{ambiguous}. Unsupported seeds are drawn from five categories -- sensor, algorithm, odometry, capability, and invalid parameter value -- and ambiguous seeds requiring clarification from five further categories -- missing numeric value, unresolved alternative, qualitative choice, conflicting requirements, and ambiguous reference.

For each seed, the local \texttt{mistral:7b} model \cite{jiang2023mistral} generated the natural-language paraphrases: three requested styles (canonical, natural, shorthand) for the train split and two (canonical, natural) for the test split, yielding 150 train missions and 100 test missions. Paraphrase generation deliberately uses a different model from \texttt{qwen2.5-coder:7b}, which remains the only model executing and being evaluated on the capability-interpretation and parameter-reasoning stages throughout this chapter, so the paraphraser and the reasoner under test are never the same model. Automatic checks rejected malformed records, duplicate texts after normalization, and records that violated the candidate schema. Every record contains a stable identifier, a source-seed identifier, the natural-language mission, the expected capability interpretation, and the expected parameter values, copied directly from the authored seed definitions rather than inferred by the paraphrasing model.

Every paraphrase is currently recorded as \texttt{pending} review. The structured reference labels carry a provenance guarantee independent of this status, since they are copied from the authored seeds rather than generated; the mission text itself, however, has not yet completed a manual quality pass. Manual inspection during this work surfaced paraphrases whose wording drifted from the intended operator command -- for example, a configuration request rewritten as a clarification question, or the expected rejection reason restated inside the mission text itself -- which a completed review pass would be expected to catch. Results computed against these datasets should be read with this outstanding review step in mind.

The dataset covers sparse requests, multi-capability requests, explicit negation, implementation selection between kinematic ICP and KISS-ICP, physical-unit conversion, and synchronized changes to multiple parameters that represent one physical property. For example, a wheel-radius request must update both the drive node and the joint-state estimator, while a request expressed in centimetres must be converted to metres.

A separate five-case file, \texttt{evaluation\_missions.jsonl}, is retained as a small diagnostic set. It is useful for quickly detecting regressions, but its size is insufficient for standalone statistical conclusions.

\section{Evaluated language-model pipeline}

The evaluation uses the three-stage reasoning pipeline described in Sections~\ref{sec:nl-reasoning} and~\ref{sec:llm-integration}: capability interpretation, parameter selection, and parameter-value reasoning, each a separate call with its own system prompt and structured response schema. All calls in the baseline use \texttt{qwen2.5-coder:7b} with temperature zero. The value-reasoning call is skipped whenever parameter selection returns \texttt{no\_change}, \texttt{unsupported}, or \texttt{needs\_clarification}.

Deterministic capability realization and ROS-system reasoning are executed only to construct the same parameter context used by the production orchestrator. The experiment stops after the third language-model boundary: it does not construct a configuration plan, render YAML, assemble launch files, or score rendered artifacts.

For reproducibility, each prediction stores the exact system prompt, user prompt, raw response, parsed structured object, latency, failure stage, and validation error. The experiment metadata additionally freezes hashes of both datasets, the three prompt templates, capability registry, system model, parameter evidence, configuration schema, and application configuration.

\section{Evaluation metrics}

The metrics distinguish partial semantic understanding from an entirely correct structured prediction.
Outcome accuracy is the proportion of missions assigned the correct terminal status and it is the single most important metric. The possible capability-stage outcomes are \texttt{valid}, \texttt{unsupported}, and \texttt{needs\_clarification}; since the train and test datasets described in Section~\ref{sec:extended-datasets} contain unsupported and ambiguous missions alongside supported ones, this metric also measures unsafe acceptance of a request that should have been rejected or referred for clarification. Unsafe execution rate isolates the most safety-relevant part of that failure mode: the fraction of missions whose gold status is \texttt{unsupported} or \texttt{needs\_clarification} for which the pipeline nonetheless reports a \texttt{valid} status and an applicable configuration change, rather than refusing or asking for clarification.
Capability exact match checks whether the system selected the correct implementation for every capability, including capabilities that were explicitly disabled. The entire prediction must match the reference; one missing, extra, or incorrect capability makes the case incorrect. Precision and recall additionally measure how many individual capability decisions were correct across the dataset.
Parameter-selection exact match checks whether the system selected exactly the expected parameter identifiers, with no missing or unnecessary parameters. Precision, recall, and $F_1$ give partial credit when only some identifiers are correct.
Parameter-value exact match checks whether the system produced the correct value for every expected parameter after applying any required unit conversion. Because the system cannot produce a value for a parameter it failed to select, this metric evaluates parameter selection and value generation together. A future experiment could provide the correct parameter identifiers in advance to evaluate value generation independently. Individual-value accuracy relaxes this to per-parameter partial credit, analogous to selection precision and recall: it is the fraction of individually expected parameter values produced correctly across the dataset, regardless of whether every other value in the same mission was also correct.
Retrieval recall at rank $k$, for $k \in \{1,3,5\}$, measures whether the correct parameter identifier appears among the top-$k$ candidates returned by the deterministic retrieval stage before selection is attempted; mean reciprocal rank averages the inverse of the correct identifier's rank across missions, so a correct match ranked second or third is still rewarded, just less than a correct match ranked first.
Joint LLM exact match requires the entire three-call pipeline to be correct: the outcome, capabilities, selected parameters, and parameter values must all match the reference. A narrower, stage-scoped end-to-end accuracy is also reported where only the parameter-selection and value-reasoning calls are evaluated together, given each mission's correct capability context rather than a live capability prediction; it should not be read as equivalent to the pipeline-wide joint metric. Validated inference completion only checks that every required model response was correctly formatted and passed the system's validation rules; it does not mean that the prediction was semantically correct.
Paraphrase consistency measures how often the natural-language paraphrases of the same seed -- three per seed in the train split, two per seed in the test split -- produce identical structured results. Group robustness is stricter because every paraphrase of a seed must produce the correct result; consistently producing the same wrong answer therefore passes consistency but fails robustness. Mean, median, and 95th-percentile latency measure the time required by all model calls made for a mission.

\section{Experimental Results}
\label{sec:experimental-progression}

Each language-model call introduced in Section~\ref{sec:nl-reasoning} is evaluated independently against the train and test datasets described in Section~\ref{sec:extended-datasets}, so that a capability-interpretation error can be distinguished from a parameter-selection or value-reasoning error rather than collapsed into one end-to-end figure. Every run below uses the current, frozen prompt files.

\subsection{Capability interpretation}

The capability-interpretation call was run in isolation, with the current \texttt{prompts/mission\_interpretation.txt} prompt, against the 150-mission train split and the 100-mission test split. Table~\ref{tab:capability-reasoning-results} reports outcome accuracy, capability exact match, and capability field micro precision, recall, and $F_1$, as defined above.

Both splits complete without a single runtime or validation error, and outcome accuracy exceeds 92\% on both, despite the train and test datasets now containing unsupported and ambiguous missions in addition to supported ones. The gap between capability exact match (90.0\%/92.0\%) and capability field micro $F_1$ (94.8\%/94.1\%) reflects a recurring pattern: most individual capability decisions are correct, but a minority of missions still miss on exactly one field, which is enough to fail the stricter exact-match criterion. Field micro recall exceeds precision on both splits (97.9\%/100.0\% versus 92.0\%/88.9\%), indicating that the model rarely omits a capability the reference expects but occasionally reports one that was not requested.

Manual review of all 23 missed cases (15 train, 8 test) shows three distinct failure patterns rather than uniform noise. Most missed cases (14 of 23) request a single invalid parameter value or a genuinely conflicting capability choice, where either the gold label and the prompt's own defaulting rule disagree on what \texttt{valid} should mean, or the model resolved a real ambiguity instead of asking for clarification. A second group (8 of 23) mis-sets the \texttt{exploration} or \texttt{odometry} field specifically on missions that name four or five capabilities at once, including plain, non-abbreviated wording, suggesting a field-tracking limit on crowded requests rather than a language-comprehension failure. The remaining case is a genuinely unsupported capability that the model accepted with default values instead of rejecting.

Retrieval is the weakest link in both splits: the correct parameter identifier is the single top-ranked candidate only 42.7\%/43.3\% of the time, though it appears within the top five for 85.4\%/88.3\% of cases. Selection and value quality are markedly stronger once the correct candidate is retrieved, with parameter-selection exact match reaching 76.5\%/86.7\% and individual-value accuracy 87.3\%/92.5\%; none of the 51 train or 30 test cases had an unsupported or ambiguous gold outcome, so an unsafe-execution rate cannot be computed for this run.

Manual review of all 18 missed cases (13 train, 5 test) again shows a small number of recurring patterns. Roughly a third (6 of 18) are pure retrieval misses: the mission asks to change an exploration or joint-state publication rate in plain language, for example ``publish a map at 2 hertz,'' but \texttt{nodes.explore.publish\_rate} or the equivalent joint-state parameter never reaches the retrieved candidate set, so selection correctly reports \texttt{no\_change} for a request that should have been \texttt{valid}. Another third (6 of 18) over-selects a plausible but unrequested sibling parameter that shares a node or component with a correctly selected one -- \texttt{wheel\_odom\_frame} alongside a wheel-separation change, or \texttt{enable\_explore\_lite} and \texttt{use\_sim\_time} alongside an unrelated request -- consistent with the component-name leakage in the retrieval scorer identified earlier in this project and only partially mitigated. Three train cases are schema-validation errors, where the model's own JSON response contradicts its declared status (for example, claiming \texttt{needs\_clarification} while also returning a partial selection) and is rejected before scoring. The remaining two cases are value-reasoning errors on an otherwise correctly selected parameter, where the reported value is consistent with an inverted or rescaled unit rather than the requested frequency, suggesting a unit-conversion slip rather than a selection failure.

The complete pipeline -- all three calls executed in sequence, each receiving only the outputs of the calls before it -- was evaluated end-to-end against the full train (150) and test (100) datasets. Unlike the two isolated evaluations above, parameter selection and value reasoning here receive the model's own predicted capability context rather than the gold one, so a capability-interpretation error can propagate into the parameter stage. Joint LLM exact match -- every stage correct simultaneously -- reaches only 65.6\%/66.0\%, well below the individual-stage exact-match figures reported above (90\%--100\% for capability, 71\%--87\% for parameter selection in isolation), and the unsafe execution rate (26.7\%/38.0\%) is the more concerning number of the two.

Classifying all 60 train and 41 test failures by which stage's output first diverges from the reference explains why the isolated-stage numbers do not predict this joint result. 23 of 60 train failures and 18 of 41 test failures show both a capability mismatch and a downstream parameter mismatch in the same mission, confirming the propagation effect noted above. A comparable share, 23 of 60 train and 17 of 41 test failures, have a correct capability object but still fail at parameter selection or value reasoning, matching the retrieval and over-selection patterns already identified in isolation. The remaining 14 train and 5 test failures have an incorrect capability object whose associated parameter output was nonetheless scored correct, since the mismatched capability field happened not to be the one the requested parameter depends on.

\section{Limitations}
\label{sec:dataset-results-limitations}

All three result tables in this chapter are a single run of one quantized local model. Temperature zero improves repeatability but does not guarantee identical outputs across inference-runtime versions or hardware, so repeated runs would be needed for variance estimates and confidence intervals, which are not yet available.

Only Table~\ref{tab:full-pipeline-results} exercises the live capability-to-parameter propagation described above; well over half of its joint-pipeline failures involve a capability mismatch (61.7\% train, 56.1\% test), and most of those also carry a parameter-stage mismatch in the same mission (62.2\% train, 78.3\% test). Its unsafe execution rate remains the most significant unresolved concern in the current system. The train and test paraphrases also remain in \texttt{pending} review, as noted in Section~\ref{sec:extended-datasets}. These limitations are turned into concrete next activities in Section~\ref{sec:next-activities}.
