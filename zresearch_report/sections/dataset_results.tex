\chapter{Dataset and Experimental Results}
\label{chap:dataset-results}

This chapter describes the construction of the AntRobot natural-language mission dataset, the evaluation protocol used for the language-model stages, and the complete sequence of recorded experiments. The experiments follow the implementation from the initial production-prompt baseline, through few-shot prompting and the unified orchestrated evaluator, to the simplified capability contract and bounded semantic parameter pipeline. Configuration rendering, generated YAML files, and generated launch files are outside the scored boundary; the reported results concern the three language-model stages and their deterministic validation.

\section{Dataset and Evaluation Methodology}

Each dataset entry began with a verified structured intent and its corresponding reference annotation. A text-generation model was then used only to express that intent in varied natural-language forms. Because the expected capabilities and parameters were defined beforehand rather than inferred by the model, the reference labels remained independent of the generated wording.

The construction process consisted of the following stages:

\begin{enumerate}
    \item Fifteen seed missions were defined from capabilities and parameters that exist in the extracted AntRobot system model. Each seed contains a canonical intent, a sparse capability annotation, any explicitly requested parameter values, and descriptive strata.
    \item For each seed, the local \texttt{qwen2.5-coder:7b} model generated ten paraphrases. The requested styles included canonical language, natural language, shorthand, imperative phrasing, negative phrasing, and multi-clause requests.
    \item Automatic checks rejected malformed records, duplicate texts after normalization, and records that violated the candidate schema.
    \item A semantic review checked that each paraphrase preserved the seed intent and did not add or remove requirements. Rejected variants were regenerated or replaced.
    \item Fourteen records required a manual language repair after semantic review. The final dataset therefore contains 136 model-generated paraphrases and 14 repaired paraphrases.
\end{enumerate}


The resulting \texttt{antrobot\_mission\_dataset\_v1.jsonl} file contains 150 missions: 15 intent groups which were manually defined with 10 paraphrases per group which were done based on an LLM. Every record contains a stable identifier, a source-seed identifier, the natural-language mission, the expected capability interpretation, and the expected parameter values. All 150 missions in this version are supported requests.

The dataset covers sparse requests, multi-capability requests, explicit negation, implementation selection between kinematic ICP and KISS-ICP, physical-unit conversion, and synchronized changes to multiple parameters that represent one physical property. For example, a wheel-radius request must update both the drive node and the joint-state estimator, while a request expressed in centimetres must be converted to metres. A separate five-case file, \texttt{evaluation\_missions.jsonl}, is retained as a small diagnostic set. It is useful for quickly detecting errors, but its size is insufficient for standalone statistical conclusions. 

The application uses one model in three specialized calls, rather than three independently trained models. All calls in the baseline use \texttt{qwen2.5-coder:7b} with temperature zero, but each call has a distinct system prompt and structured response schema:
\begin{enumerate}
    \item \textbf{Capability interpretation} identifies mapping, navigation, exploration, and odometry requirements and chooses an overall status.
    \item \textbf{Parameter identification} receives a bounded, retrieved parameter context and selects the identifiers that must change.
    \item \textbf{Value reasoning} receives the selected parameters and proposes their new values. This call is skipped when the second stage returns \texttt{no\_change}, \texttt{unsupported}, or \texttt{needs\_clarification}.
\end{enumerate}

Deterministic capability realization and ROS-system reasoning are executed only to construct the same parameter context used by the production orchestrator. The experiment stops after the third language-model boundary. It does not construct a configuration plan, render YAML, assemble launch files, or score rendered artifacts. For reproducibility, each prediction stores the exact system prompt, user prompt, raw response, parsed structured object, latency, failure stage, and validation error.

The metrics distinguish partial semantic understanding from an entirely correct structured prediction.
Outcome accuracy is the proportion of missions assigned the correct terminal status and it is the single most important metric. The possible capability-stage outcomes are \texttt{valid}, \texttt{unsupported}, and \texttt{needs\_clarification}. Since the current benchmark contains only supported missions, this metric measures valid-request acceptance and does not measure unsafe acceptance of unsupported requests.
Capability exact match checks whether the system selected the correct implementation for every capability, including capabilities that were explicitly disabled. The entire prediction must match the reference; one missing, extra, or incorrect capability makes the case incorrect. Precision and recall additionally measure how many individual capability decisions were correct across the dataset.
Parameter-selection exact match checks whether the system selected exactly the expected parameter identifiers, with no missing or unnecessary parameters. Precision, recall, and $F_1$ give partial credit when only some identifiers are correct.
Parameter-value exact match checks whether the system produced the correct value for every expected parameter after applying any required unit conversion. Because the system cannot produce a value for a parameter it failed to select, this metric evaluates parameter selection and value generation together. A future experiment could provide the correct parameter identifiers in advance to evaluate value generation independently.
Joint LLM exact match requires the entire pipeline to be correct: the outcome, capabilities, selected parameters, and parameter values must all match the reference. Validated inference completion only checks that every required model response was correctly formatted and passed the system's validation rules; it does not mean that the prediction was semantically correct.
Paraphrase consistency measures how often all ten natural-language versions of the same intent produce identical structured results. Group robustness is stricter because all ten versions must produce the correct results; consistently producing the same wrong answer therefore passes consistency but fails robustness. Mean, median, and 95th-percentile latency measure the time required by all model calls made for a mission.

The four columns are successive system revisions rather than a controlled single-factor ablation. In particular, the two early artifacts use the original dataset annotation and top-12 graph context, whereas the orchestrated artifacts use revised capability annotations, top-10 semantic retrieval, and production-like composition of the independently evaluated stages. The comparison therefore documents engineering progress of the complete system; it does not assign the final gain to one isolated change.

The baseline used the original capability representation, top-12 graph retrieval, and the first production prompts. Capability reasoning showed partial understanding, with 76.1\% micro $F_1$, but complete capability objects were correct in only 38.7\% of missions. Parameter grounding was the dominant failure: parameter-selection exact match was 0.7\%, joint exact match was zero, and only 43.3\% of missions completed all applicable validated calls.

The few-shot run held the original model and retrieval configuration fixed and added systematic demonstrations to all three prompts. These examples clarified capability-only requests, bounded identifier selection, coupled physical parameters, and unit conversion. Outcome accuracy increased from 63.3\% to 90.7\%, and parameter micro $F_1$ increased from 1.6\% to 11.8\%. However, exact parameter accuracy did not improve and validated completion fell to 18.0\%. The intervention improved partial semantic recognition but also encouraged more attempted outputs that violated strict schema or grounding checks. This motivated structural separation and deterministic context control rather than relying on examples alone.

The unified run evaluated the three agents in the same order and with the same intermediate contracts used by the application. Parameter retrieval was reduced to ten candidates and enriched with LLM-derived aliases, user expressions, behavioral descriptions, constraints, and typed relationships. Retrieval ranks and scores were kept outside the model-facing context; capability realization restricted the catalogue to active components; capability-only requests were prevented from becoming invented launch-argument changes; and selection and value generation were separated. A single validation-guided retry was internal to the pipeline. These changes raised capability exact match to 75.3\%, parameter-selection exact match to 53.3\%, joint exact match to 40.0\%, and validated completion to 94.7\%. The run demonstrated successful composition of the independently tested agents, but capability errors still propagated into retrieval and parameter reasoning.

The final recorded experiment simplified capability output to four direct capability values. Each value is the selected implementation, while \texttt{null} is reserved for an explicitly disabled capability. The capability prompt preserves registry defaults for unmentioned capabilities, changes an implementation only when requested, distinguishes capability selection from parameter tuning, and omits inference provenance such as \texttt{selection\_basis}. Dataset annotations and deterministic realization were updated to the same contract. Additional prompt rules addressed negation and short parameter-only missions, while active-component filtering, semantic top-10 retrieval, bounded parameter selection, value-only reasoning, and deterministic validation remained in place.

This final step produced the strongest result in every semantic correctness measure: capability exact match reached 96.7\%, parameter-selection and parameter-value exact match reached 88.7\%, and 132 of 150 missions were jointly exact, corresponding to 88.0\%. Only two missions ended in runtime or validation errors, and 98.7\% completed the validated pipeline. Nine of the fifteen seed groups were correct for all ten paraphrases. Mean latency increased to 8.56 seconds because more missions successfully reached all applicable reasoning stages and the internal correction path could be exercised.

For parameter-changing missions specifically, the minimal-contract artifact reports retrieval recall of 65.8\% at rank one, 98.7\% within the top three, and 100\% within the top five. Selection exact-set accuracy over the 80 parameter-change cases was 83.8\%, individual-value accuracy was 96.4\%, and complete-value-set accuracy was 83.8\%. This supports the staged design: once the correct bounded identifiers are available, generating their values is considerably more reliable than identifying the complete parameter set.

\textbf{Initial baseline experiment} evaluated the production prompts with \texttt{qwen2.5-coder:7b} without tuning them on the benchmark. The model showed partial capability understanding, reaching 76.1\% capability micro $F_1$, but complete capability predictions were correct for only 38.7\% of generated missions. Parameter identification was the main limitation: exact selection reached 0.7\%, no mission was jointly correct, and only 43.3\% completed all validation stages. The baseline therefore showed that the original prompts could recognize parts of an intent but could not reliably produce complete, grounded parameter outputs.

\textbf{Few-shot prompt experiment} kept the model and evaluation setup unchanged but added demonstrations of capability-only, parameter-only, combined, coupled-parameter, and unit-conversion requests. These examples improved outcome accuracy from 63.3\% to 90.7\% and parameter micro $F_1$ from 1.6\% to 11.8\%, showing better partial recognition of the requested changes. However, exact parameter selection remained 0.7\%, no mission was jointly correct, and validated completion fell to 18.0\%. Examples alone were therefore insufficient, motivating a more structured pipeline with tighter context and validation control.

\textbf{Unified pipeline experiment} evaluated the three reasoning stages in the same sequence used by the application. It limited retrieval to ten semantically enriched candidates, filtered parameters by active components, separated parameter selection from value generation, and added one validation-guided retry. Capability exact match increased to 75.3\%, parameter-selection exact match to 53.3\%, joint exact match to 40.0\%, and validated completion to 94.7\%. This showed that structured orchestration greatly improved reliability, although capability errors could still affect later stages.

\textbf{Minimal-contract experiment} simplified capability output to four direct values, using an implementation identifier for an active capability and \texttt{null} only for explicit deactivation. Capability exact match reached 96.7\%, parameter-selection and parameter-value exact match reached 88.7\%, joint exact match reached 88.0\%, and validated completion reached 98.7\%. This was the strongest configuration and showed that a simpler output contract substantially reduced errors throughout the pipeline.

\section{Limitations and next experiments}
Each artifact is a single run of one quantized local model. Temperature zero improves repeatability but does not guarantee identical outputs across inference-runtime versions or hardware, so repeated runs are needed for variance estimates and confidence intervals. The progression also combines prompt, contract, dataset-label, retrieval, and orchestration changes. It demonstrates the improvement of the implemented system, but controlled ablations are required to quantify the contribution of each intervention independently.

The dataset still requires final independent author review, and its all-supported composition prevents measurement of unsupported-request rejection, clarification recall, or unsafe execution. Subsequent experiments should add independently annotated unsupported and ambiguous missions, repeat the final pipeline, compare deterministic-only and LLM-enriched retrieval under the same contract, evaluate value reasoning with oracle parameter selection, and compare alternative local models against the frozen minimal-contract pipeline.
